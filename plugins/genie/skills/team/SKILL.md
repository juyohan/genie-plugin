# 팀 병렬 실행 — 루트 오케스트레이터

<input_document> #$ARGUMENTS </input_document>

`--add gemini` (또는 `--add gem`) 플래그가 있으면: gem 도구로 의존성 그래프 검토 요청 후 결과 통합.

---

## 1. 플랜 로드

1. `$ARGUMENTS`가 파일 경로면 해당 플랜 사용. 비어 있으면 `docs/plans/`에서 가장 최근 `status: active` 플랜 선택
2. 플랜이 없으면 안내 후 종료:
   > "`/genie:plan`으로 플랜을 먼저 작성하세요."
3. 플랜의 `Implementation Units` 섹션에서 추출:
   - 각 U-ID, 이름, 설명
   - 담당 파일 목록
   - `Depends on:` 필드 (없으면 독립 단위)
   - `Test Scenarios` 및 `Verification` 기준

---

## 2. 의존성 그래프 및 웨이브 구성

추출한 단위로 DAG를 구성하고 실행 웨이브를 산출합니다:

```
웨이브 N = 이전 웨이브에서만 의존하거나 의존성 없는 단위들의 집합
```

분석 결과 출력:
```
웨이브 1 (병렬 3): U1 · U2 · U4
웨이브 2 (병렬 2): U3(→U1) · U5(→U2)
웨이브 3 (직렬 1): U6(→U3,U5)
총 3 웨이브 / 6 단위
```

단위가 2개 이하이거나 모든 단위가 선형 종속이면:
> "병렬화 이점이 없습니다. `genie:work`를 대신 사용하는 것을 권장합니다."
계속 진행 여부를 사용자에게 묻습니다.

---

## 3. 워커 레지스트리 및 핸드오프 초기화

활성 워커를 메모리에서 추적하고 핸드오프 디렉토리를 준비합니다:

```bash
mkdir -p .agent-handoff
```

| 키 | 값 |
|----|----|
| `worker-U{id}` | 에이전트 이름 — SendMessage 및 핸드오프 대상 식별자 |

`.agent-handoff/`를 `.gitignore`에 추가합니다 (임시 상태 파일, 커밋 불필요):
```bash
grep -qxF '.agent-handoff/' .gitignore 2>/dev/null || echo '.agent-handoff/' >> .gitignore
```

---

## 4. 웨이브 실행

각 웨이브를 순서대로 실행합니다.

### 4-1. 파일 겹침 확인 (필수 안전장치)

웨이브 내 단위들의 파일 목록을 교차 확인합니다.

**겹치는 파일이 있는 단위는 직렬로 강등합니다** (경고가 아닌 강제):
```
U3 · U5 → 직렬 강등 (파일 겹침: src/shared/utils.ts)
```

### 4-2. 컨텍스트 패키지 빌드

각 단위를 파견하기 전, 해당 단위에 필요한 정보만 담은 컨텍스트 패키지를 텍스트 변수로 빌드합니다.

```markdown
# 컨텍스트 패키지: <unit-id>

## 이 단위에서 할 일
<플랜의 해당 U-ID 설명, Execution note, 검증 기준>

## 담당 파일
<이 단위가 수정할 파일 목록만>

## 건드리지 않을 것
<다른 단위 담당 파일 명시 — 같은 브랜치이므로 실수로 수정하면 충돌 발생>

## 선행 단위 결과 (있는 경우)
<선행 웨이브 워커의 "후속 단위에 전달할 사항">
※ 첫 번째 웨이브는 이 섹션 없음

## 테스트 시나리오
<플랜의 이 단위 Test Scenarios>

## 프로젝트 컨벤션
<AGENTS.md 또는 CLAUDE.md의 핵심 규칙 요약>

## 제약
- git 명령 금지 (stage, commit, push 모두 금지) — 오케스트레이터가 처리
- 담당 파일 외 수정 금지
- 완료를 스스로 선언하지 말 것 — 체크포인트를 보고하고 오케스트레이터 판단을 기다림
```

### 4-3. 워커 파견 (병렬 단위)

각 병렬 단위에 대해 컨텍스트 패키지를 프롬프트에 담아 직접 파견합니다:

**워커 파견** (`run_in_background: true`):
- 에이전트 이름: `worker-U{id}`
- 프롬프트: 4-2에서 빌드한 컨텍스트 패키지 전체 텍스트
- 워크트리 없음 — 현재 브랜치에서 직접 실행
- 워커는 파일 읽기/쓰기만 수행 (git 명령 금지)

모든 워커 응답(첫 번째 체크포인트)을 기다립니다.

### 4-4. 직렬 단위 인라인 실행

직렬 강등된 단위는 현재 브랜치에서 직접 구현합니다.
동일하게 컨텍스트 패키지를 먼저 빌드하고 체크포인트 기반으로 진행합니다.

### 4-5. 체크포인트 평가 및 오케스트레이터 결정

워커로부터 체크포인트를 수신할 때마다 오케스트레이터가 아래 기준으로 평가하고 결정합니다:

#### 체크포인트 수신 형식

```
## 체크포인트
단계: <현재 완료된 단계명>
진행률: <0-100%>

## 완료된 작업
<이번 체크포인트까지 완료한 내용>

## 수정된 파일
- path/to/file — 변경 내용

## 미완료 작업
<아직 남은 작업>

## 오케스트레이터에게
<판단이 필요한 사항, 불확실한 부분, 전문가 의견 필요 여부>
```

#### 오케스트레이터 결정 기준

| 상황 | 결정 | 행동 |
|------|------|------|
| 정상 진행 중 | **계속** | `SendMessage`로 다음 단계 지시 |
| 다른 전문 에이전트가 더 적합 | **위임** | 핸드오프 파일 생성 → 새 에이전트 파견 |
| 범위 외 파일 수정 감지 | **중단** | 해당 파일 되돌리고 재지시 |
| 모든 작업 완료 | **완료** | 4-6 웨이브 커밋으로 진행 |

#### 계속 결정 시

```
SendMessage({to: "worker-U{id}", message: "다음 단계 진행해. {추가 지시 사항}"})
```

#### 위임 결정 시 — 핸드오프 프로토콜

1. 핸드오프 상태 파일 생성:

```markdown
# 핸드오프 상태: <unit-id>
from: worker-U{id}
to: <다음 에이전트 종류>
reason: <위임 이유>
timestamp: <ISO 8601>

## 완료된 작업
<worker가 완료한 내용>

## 미완료 작업 (인수인계)
<다음 에이전트가 이어받아야 할 작업>

## 수정된 파일 현황
- path/to/file — 현재 상태 한 줄 설명

## 컨텍스트
<다음 에이전트가 알아야 할 결정사항, 인터페이스, 주의사항>

## 오케스트레이터 지시
<다음 에이전트에게 전달할 구체적 작업 지시>
```

파일 저장: `.agent-handoff/<unit-id>.md`

2. 위임 이유에 따라 전문 에이전트 선택 후 파견:

| 위임 이유 | subagent_type |
|-----------|--------------|
| 보안 취약점 의심 | `genie:security` |
| 성능 최적화 필요 | `genie:perf` |
| 언어별 전문 리뷰 | `genie:ts` / `genie:py` / `genie:go` 등 |
| 리팩토링 필요 | `genie:refactor` |
| 일반 구현 계속 | `genie:unit-worker` (새 컨텍스트로 재파견) |

```
Agent({
  name: "specialist-U{id}",
  subagent_type: "<위임 이유에 맞는 타입>",
  prompt: ".agent-handoff/<unit-id>.md 파일을 읽고 미완료 작업을 이어받아 완료하세요."
})
```

### 4-6. 웨이브 커밋 (오케스트레이터)

웨이브 내 모든 단위 완료 판정 후 오케스트레이터가 한 번에 커밋합니다:

```bash
git add <이번 웨이브 모든 단위의 수정 파일>
git commit -m "feat: [Wave {N}] {U-ID 목록} 구현

- U1: {단위명} ({수정 파일})
- U2: {단위명} ({수정 파일})
- U4: {단위명} ({수정 파일})"
```

**커밋 직후 즉시 테스트 실행** — 실패 시:

1. 빠른 수정: 수정 후 재커밋, 테스트 재실행
2. 복잡한 실패: 웨이브 커밋 전체 롤백
   ```bash
   git revert HEAD --no-edit
   ```
   롤백 후 사유와 관련 단위 ID를 사용자에게 출력하고 계속 진행 여부를 묻습니다.

---

## 5. 최종 검증

모든 웨이브 완료 후:

1. 전체 테스트 스위트 실행
2. 린터 실행
3. 플랜의 `Requirements` 항목 전체 충족 여부 확인
4. `.agent-handoff/` 정리 (gitignore 적용 중이므로 선택적)
5. 플랜 frontmatter `status: active → completed` 전환

---

## 6. 완료 보고

```
팀 실행 완료
  웨이브:    3 (총 6개 단위)
  병렬 처리: U1 · U2 · U4 / U3 · U5
  직렬 처리: U6
  위임:      U1 → security-reviewer (인증 로직 보안 검토)
  커밋:      3개 (웨이브별)
  실패:      없음
  다음 단계: /genie:review
```

`/genie:review`를 다음 단계로 권장합니다.
