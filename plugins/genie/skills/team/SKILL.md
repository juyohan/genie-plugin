# genie:team — 동적 팀 반복 토론 오케스트레이션

전문가 역할을 동적으로 구성하고, 에이전트끼리 서로의 주장에 반응하며 수렴할 때까지 반복 토론합니다.

---

## Phase 0 — 스코프 파악 (Lead 단독 실행)

에이전트를 띄우기 전에 Lead가 직접 관련 파일을 특정한다. 에이전트는 이 목록을 시작점으로 사용한다.

**1. 기존 문서 우선 확인**

주제와 관련된 brainstorm·plan 문서가 있으면 그것을 1차 스코프로 삼는다:

```bash
ls docs/brainstorms/$(date +%Y/%m)/
ls docs/plans/$(date +%Y/%m)/
```

**2. 코드·파일 탐색**

문서가 없거나 보완이 필요하면 키워드로 직접 탐색한다 (최대 10개):

```bash
grep -r "{핵심 키워드}" --include="*.{js,ts,py,md}" -l | head -10
git log --oneline -10 -- {관련 경로}
```

**3. 스코프 목록 확정**

탐색 결과에서 가장 관련도 높은 파일 5~10개를 추린다. 이후 모든 에이전트에게 이 목록을 전달한다.

```
[스코프] 다음 파일을 기반으로 분석합니다:
- {파일 경로 1}
- {파일 경로 2}
- ...
```

## Phase 1 — 주제 파악 및 역할 결정

`$ARGUMENTS`가 있으면 그것을 주제로 사용. `--rounds N`이 있으면 최대 라운드를 N으로 설정 (기본값: 3).

**역할 결정 기준:**

| 복잡도 | 에이전트 수 |
|--------|------------|
| 단일 관심사 | 2개 |
| 일반적인 설계·결정 | 3개 |
| 여러 이해관계자·도메인 | 4개 (최대) |

**역할 후보 (주제에 맞게 선택):**

| 분야 | 역할 예시 |
|------|-----------|
| 기술 | 아키텍트, 보안 전문가, 성능 엔지니어, 테스트 전문가 |
| 도메인 | UX, 비즈니스 로직, 데이터 모델링 |
| 비판적 | 악마의 변호인, 유지보수 관점, 단순화 관점 |

역할 확정 후 사용자에게 보고하고 실행 환경을 준비한다:

```bash
RUN_ID=$(date +%Y%m%d-%H%M%S)
mkdir -p /tmp/genie/team/$RUN_ID/round-1
```

```
[팀 구성] {역할1} / {역할2} / {역할3} — 최대 {N}라운드
```

## Phase 2 — 반복 토론

### Round 1: 초기 분석

각 에이전트를 **동시에** 호출한다. 프롬프트:

```
역할: {역할명}
주제: {검토 주제}
관점: {이 역할의 핵심 시각}

분석 전 다음을 수행하십시오:
1. Lead가 전달한 스코프 파일 목록을 읽어 현재 상태를 파악하십시오. 추가로 필요한 파일이 있으면 확장할 수 있지만, 스코프 목록을 시작점으로 삼으십시오.
2. 주장은 반드시 읽은 파일·코드·공식 문서를 근거로 하십시오.
3. "~인 것 같다", "~일 수 있다" 형태의 추측성 표현은 사용하지 마십시오.
   근거가 없으면 "확인 필요"로 명시하십시오.

초기 분석을 작성하고 아래 파일에 저장하십시오:
경로: /tmp/genie/team/{run-id}/round-1/{role-slug}.md

파일 형식:
## 역할: {역할명} | Round 1

### 참고 자료
- {읽은 파일 경로 또는 문서 출처}

### 핵심 발견
- {발견 내용} — 근거: {파일명:라인 또는 출처}

### 주요 우려 사항
- {우려 내용} — 근거: {파일명:라인 또는 출처}

### 권고 사항
- ...

CONCLUDE: no
```

### Round 2~N: 반응 및 수렴

이전 라운드 디렉토리 생성 후 각 에이전트를 **동시에** 호출한다:

```bash
mkdir -p /tmp/genie/team/$RUN_ID/round-{N}
```

프롬프트:

```
역할: {역할명}
주제: {검토 주제}

다른 에이전트들의 Round {N-1} 결과를 읽으십시오:
{이전 라운드의 다른 에이전트 파일 경로 목록}

읽은 내용을 바탕으로:
1. 동의하는 부분을 확인하십시오.
2. 반박하거나 보완할 부분이 있으면 코드·문서·파일을 직접 읽어 근거를 확보한 뒤 제시하십시오.
3. 상대의 주장이 특정 파일이나 동작을 근거로 한다면 해당 내용을 직접 확인하십시오.
4. 추측성 반박은 허용하지 않습니다. 근거가 없으면 "확인 필요"로 명시하십시오.
5. 새로운 인사이트가 없으면 CONCLUDE: yes로 표시하십시오.

결과를 아래 파일에 저장하십시오:
경로: /tmp/genie/team/{run-id}/round-{N}/{role-slug}.md

파일 형식:
## 역할: {역할명} | Round {N}

### 추가 참고 자료
- {이번 라운드에 새로 읽은 파일 또는 출처}

### 이전 라운드 반응
- {동의 / 반박 / 보완} — 근거: {파일명:라인 또는 출처}

### 입장 업데이트
- {변경된 부분 또는 "입장 유지 — 이유"}

### 새로운 인사이트
- {없으면 생략}

CONCLUDE: yes/no
```

### 종료 조건 판단 (각 라운드 후 Lead가 확인)

```bash
grep "CONCLUDE:" /tmp/genie/team/$RUN_ID/round-{N}/*.md
```

- **전원 `CONCLUDE: yes`** → Phase 3으로 진행
- **최대 라운드 도달** → Phase 3으로 진행
- **하나라도 `CONCLUDE: no`** → 다음 라운드 실행

## Phase 3 — 최종 종합 (Lead)

모든 라운드 파일을 읽고 수렴 과정을 반영한 최종 결론을 작성한다:

```bash
cat /tmp/genie/team/$RUN_ID/round-*/*.md
```

**출력 형식:**

```
## 팀 검토 결과

**주제**: {한 줄 요약}
**구성**: {역할1} / {역할2} / ...
**진행**: {N}라운드 ({수렴 이유: 전원 동의 / 최대 라운드 도달})

### 토론 흐름
{어떤 주장이 어떻게 발전하거나 수렴했는지 핵심 요약}

### 합의된 방향
{공통으로 수렴된 결론 또는 트레이드오프}

### 미해결 이견
{수렴되지 않은 부분이 있으면 정리, 없으면 생략}

### 다음 액션
- [ ] {구체적 실행 항목}
```

---

## 언제 사용하는가

- 중요한 아키텍처·설계 결정
- 복잡한 버그 원인 분석
- 다각도 검토가 필요한 기능 제안
- 트레이드오프가 명확하지 않은 선택

## 언제 사용하지 않는가

- 단순 파일 편집, 버그 수정
- 이미 방향이 정해진 작업
- 빠른 답변이 필요한 사소한 질문
